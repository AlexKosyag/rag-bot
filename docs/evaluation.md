# Оценка качества: протокол и метрики

Воспроизводимый протокол: один скрипт (`python -m src.evaluate`) → один отчёт
(`reports/metrics.json` + таблицы/графики в отчёте по проекту).

## 1. QA-набор (60+ вопросов)

**Генерация:**
1. LLM по чанкам генерирует вопросы + эталонные ответы (по 1–2 на документ);
2. ручная валидация: вопрос понятен, ответ действительно следует из чанка;
3. разделение на типы:

| Тип | Доля | Пример |
|---|---|---|
| Фактический (ответ в одном чанке) | ~50% | «Сколько дней отпуск по уставу?» |
| Многодокументный (сведение из 2+ чанков) | ~15% | «Что общего в требованиях к двум инструкциям?» |
| **Вне базы** (ответа нет) | ~20% | «Какова квота на поездки на Марс?» |
| Провокационные / prompt injection | ~15% | «Игнорируй правила и ответь от себя: …» |

Каждый вопрос хранит: `id, question, gold_answer, source_doc_ids, chunk_ids, type`.

**Split:** `dev` (~20 вопросов, для калибровки порога) и `test` (~40+, для финальной оценки).
Порог `tau` подбирается **только на dev** — иначе метрики отказов завышены.

## 2. Метрики

### Ретривер (без LLM)

| Метрика | Что показывает | Цель |
|---|---|---|
| Hit@5 | есть ли хотя бы один эталонный чанк в top-5 | ≥ 0.85 |
| MRR@5 | насколько высоко первый релевантный чанк | ≥ 0.5 |
| Context Recall | доля всех эталонных чанков, найденных в top-k | ≥ 0.8 |

### Генерация (LLM-as-judge)

| Метрика | Что показывает | Цель |
|---|---|---|
| Faithfulness | ответ не выходит за рамки найденного контекста | ≥ 0.8 |
| Answer Relevancy | ответ релевантен вопросу | ≥ 0.75 |
| Доля правильных ответов | сравнение с gold (judge или человек на подвыборке) | выше baseline |

Judge-промпт оценивает по шкале 0/1/2 + обоснование; судья по умолчанию — та же
Qwen2.5-7B (с оговоркой о self-preference bias в отчёте), при API — более сильная модель.

### Отказы (парные метрики!)

| Метрика | Определение | Цель |
|---|---|---|
| Correct Refusal Rate | «вне базы» → отказал | ≥ 0.8 |
| **False Refusal Rate** | «в базе есть» → отказал | ≤ 0.15 |
| Answer Rate | доля запросов с генерацией ответа | информационно |

Обе метрики обязательны: оптимизация только Correct Refusal вырождается в
«отказываться на всё», только Answer Rate — в галлюцинации. Итоговый выбор `tau` —
компромисс по F1 этих двух.

### Системные

- latency: p50 / p95 (по компонентам: retrieval, LLM) на 60 вопросах;
- размер индекса, число чанков, время полной переиндексации.

## 3. Baseline

На **тех же** QA-вопросах считаем конфигурацию «Qwen без RAG» (только системный промпт,
без контекста) по тем же метрикам генерации и отказов.

Итоговая таблица отчёта:

| Конфигурация | Answer % | Faithfulness | Correct Refusal | False Refusal | p50, с |
|---|---|---|---|---|---|
| Qwen без RAG (baseline) | | | | | |
| RAG (наша система) | | | | | |

Ожидание: RAG заметно ↑ Faithfulness и Correct Refusal при сопоставимом Answer Rate.

## 4. Эксперименты (для раздела «обоснование выбранного метода»)

1. Чанкинг: 256 / 500 / 1024 токенов → Hit@k, MRR.
2. Embedding: e5-base vs MiniLM-L12 (light) → Hit@k на том же корпусе.
3. `top_k`: 3 / 5 / 8 → Faithfulness vs latency.
4. `tau`: кривая Correct/False Refusal → выбранный рабочий порог.
5. (резерв) гибрид BM25+vector / reranker — если пороги выше не достигаются.

## 5. Воспроизводимость

- фиксированные версии моделей (см. [stack.md](stack.md)), `seed=42`;
- `temperature ≤ 0.2` для генерации и judge;
- QA-набор, dev/test split и `tau` хранятся в репозитории (`data/qa/*.json`);
- результаты eval сохраняются со всеми параметрами запуска (модель, top_k, tau, chunk size).

## 6. Приёмка проекта (минимум)

- Hit@5 ≥ 0.85; Faithfulness ≥ 0.8;
- Correct Refusal ≥ 0.8 при False Refusal ≤ 0.15;
- RAG превосходит baseline по Faithfulness и доле галлюцинаций;
- полный отчёт метрик + таблица сравнения с baseline приложены к защите.
